## 1 引言

### 1.1 编写目的

本文档在《软件概要设计说明书》的基础上，细化了 **doinb 视频播放与内容服务平台** 各子系统与功能模块的设计，便于开发团队理解系统各部分的详细功能、处理逻辑与界面交互，并作为编码实现与测试的依据。

预期读者：项目开发小组的开发人员、测试人员及项目管理人员。

### 1.2 背景

- **待开发软件系统名称**：doinb 视频播放与内容服务平台  
- **任务提出者**：软件工程课程组  
- **开发者**：第 9 组项目开发小组  
- **用户**：普通视频观众、内容发布者、系统管理员  
- **运行该软件的计算站（中心）**：课程组提供的云主机或实验室服务器；用户通过 PC、平板、智能手机上的现代浏览器以 Web 方式访问  

### 1.3 术语表

| 术语 | 定义 |
| :--- | :--- |
| doinb | 本课程项目开发的视频播放与内容服务类 Web 系统 |
| 用户 | 系统的最终使用者，包括普通观众与内容发布者 |
| B/S 架构 | Browser/Server，浏览器/服务器架构 |
| RESTful API | 基于 HTTP 协议、以资源为中心的接口风格 |
| JWT | JSON Web Token，用于身份验证与授权的令牌机制 |
| 点播（VOD） | 用户按视频 ID 拉取已上传视频流进行观看 |
| 直播 | 主播推流、观众实时拉流观看的在线场景 |
| 订阅 | 用户关注某发布者或频道后，在订阅视图中获取其内容更新 |
| MinIO | 可选的对象存储服务，用于存放视频、封面等大文件 |

## 3 功能模块设计

> **模块编号说明**：本节模块编号 M1～M6 沿用《软件概要设计说明书》的设计模块编号；实现阶段按代码组织进一步细分为 M1～M10（新增评论、赞踩、搜索、通知、私信、管理员审核等独立模块），两者对应关系见《需求追溯矩阵》2.2 节。

### 3.1 用户与权限管理模块

| 项目 | 说明 |
| :--- | :--- |
| **模块编号** | M1 |
| **模块名称** | 用户与权限管理模块 |
| **输入** | 用户注册信息（用户名、密码、邮箱/手机号等）；登录凭据；个人资料修改请求；退出登录请求 |
| **处理** | **注册**：校验用户名唯一性、密码强度及必填项，通过后写入 `users` 表。**登录**：校验凭据，成功后签发 JWT 并返回用户信息与角色。**资料修改**：鉴权后更新昵称、头像、简介等字段。**权限控制**：按角色（普通用户、发布者、管理员）控制发布、直播、管理入口可见性 |
| **算法描述** | **注册算法**：`SELECT` 检查用户名是否存在 → 密码哈希（如 BCrypt）→ `INSERT` 用户记录。**登录算法**：按用户名查询 → 比对密码哈希 → 生成 JWT（含用户 ID、角色、过期时间）。**权限算法**：解析请求头 Token → 校验签名与有效期 → 比对路由所需角色 |
| **输出** | 注册/登录成功或失败提示；JWT 及用户基本信息；资料更新结果；与角色相关的菜单与接口可用状态 |

### 3.2 视频播放模块

| 项目 | 说明 |
| :--- | :--- |
| **模块编号** | M2 |
| **模块名称** | 视频播放模块 |
| **输入** | 列表/推荐查询参数（分页、分类）；视频 ID；播放、暂停、进度跳转、清晰度切换（若实现）；历史查询请求 |
| **处理** | **浏览**：按条件查询 `videos` 表中已发布记录并分页返回。**播放**：校验视频状态与访问权限，返回可播放 URL 或流地址及元数据。**历史**：登录用户播放时更新或插入 `play_history`（用户 ID、视频 ID、进度、时间） |
| **算法描述** | **列表算法**：`WHERE status = 已发布` + 排序（时间/热度）+ `LIMIT/OFFSET`。**播放算法**：根据 `video_url` 或对象存储路径生成访问地址；可选 CDN/签名 URL。**历史算法**：`INSERT ... ON DUPLICATE KEY UPDATE` 更新进度与 `update_time` |
| **输出** | 视频列表与详情；播放地址或错误说明；播放历史列表 |

### 3.3 直播模块

| 项目 | 说明 |
| :--- | :--- |
| **模块编号** | M3 |
| **模块名称** | 直播模块 |
| **输入** | 直播列表查询；直播间 ID；进入/离开直播间事件；互动内容（弹幕/评论，以实现为准） |
| **处理** | **列表**：查询 `live_rooms`，按 `is_live`、计划时间等返回。**观看**：加载直播间信息与拉流地址，前端播放器拉流。**互动**：鉴权后校验内容长度与频率，写入评论或弹幕表并供前端轮询/推送刷新 |
| **算法描述** | **列表算法**：查询正在直播与预告房间，按状态排序。**拉流算法**：根据 `stream_key` 或配置的推流服务生成 HLS/FLV 等播放地址。**互动算法**：敏感词简单过滤 → 落库 → 返回最新 N 条互动记录 |
| **输出** | 直播列表与房间详情；媒体流地址或不可用提示；互动发送结果与更新后的互动区 |

### 3.4 订阅模块

| 项目 | 说明 |
| :--- | :--- |
| **模块编号** | M4 |
| **模块名称** | 订阅模块 |
| **输入** | 被关注发布者/频道 ID；订阅或取消操作；订阅列表与动态查询（含分页） |
| **处理** | **订阅/取消**：在 `subscriptions` 表中插入或删除关注关系，保证同一用户对同一目标不重复订阅。**动态展示**：根据当前用户订阅列表，关联查询被关注者最新视频或直播并分页返回 |
| **算法描述** | **订阅算法**：`INSERT` 前检查是否已存在 `(follower_id, target_id)`；取消时 `DELETE`。**动态算法**：`JOIN subscriptions` 与 `videos`/`live_rooms`，按 `create_time` 降序分页 |
| **输出** | 订阅/取消成功状态；订阅列表；订阅动态 Feed |

### 3.5 视频发布与编辑模块

| 项目 | 说明 |
| :--- | :--- |
| **模块编号** | M5 |

| **算法描述** | **上传算法**：分片或直传至存储 → 返回存储路径 → 事务写入元数据。**编辑算法**：校验 `author_id` 与当前用户一致或管理员 → `UPDATE`。**状态算法**：`status` 字段流转：审核中 → 已发布 → 已下架 |
| **输出** | 上传进度与结果；视频管理列表；保存/删除/上下架操作反馈 |

### 3.6 评论与搜索模块

| **输出** | 评论列表与发表结果；搜索结果页（视频/直播/频道等）及空结果提示 |

## 4 界面设计

### 4.1 外部界面设计

本节描述系统与外部实体（用户浏览器、数据库、对象存储等）之间的功能与数据接口。

#### 4.1.1 视频播放页面

**功能接口：**

- **浏览视频**：用户通过首页、推荐区或分类入口请求视频列表。  
- **播放视频**：用户点击某视频进入详情页并发起播放，系统返回流地址与元数据。  
- **记录历史**：登录用户在播放过程中上报进度，系统更新播放历史。

**数据接口：**

- **视频信息库（`videos`）**：提供标题、封面、作者、状态、存储路径等。  
- **播放历史库（`play_history`）**：存储用户 ID、视频 ID、进度与更新时间。  
- **对象存储/文件系统**：提供视频文件与封面的实际读写。

#### 4.1.2 直播观看页面

**功能接口：**

- **直播列表**：用户打开直播入口，获取当前或计划中的直播间列表。  
- **进入观看**：用户选择直播间，加载直播信息与拉流地址。  
- **基础互动**：在允许场景下发送弹幕或评论类互动信息。

**数据接口：**

- **直播间库（`live_rooms`）**：提供标题、主播、流密钥、是否直播中。  
- **评论/互动库（`comments` 或扩展表）**：存储直播场景下的互动记录。  
- **流媒体服务**：提供推流/拉流地址（自建或第三方，以实现为准）。

#### 4.1.3 视频发布与管理页面

**功能接口：**

- **上传视频**：发布者选择文件并填写标题、描述、封面等，提交上传。  
- **编辑元数据**：对已发布视频修改标题、描述、封面等。  
- **内容管理**：对视频执行删除或上下架操作。

**数据接口：**

- **视频信息库（`videos`）**：持久化元数据与状态。  
- **对象存储**：接收视频与封面二进制文件。  
- **用户库（`users`）**：校验发布者身份与角色。

#### 4.1.4 评论与搜索页面

**功能接口：**

- **发表评论**：用户在视频或直播详情下提交评论。  
- **查看评论**：按目标 ID 分页加载评论列表。  
- **关键词搜索**：用户输入关键词，系统返回视频、直播等相关结果。

**数据接口：**

- **评论库（`comments`）**：存储评论内容及关联目标。  
- **视频/直播元数据库**：作为搜索的数据源。  
- **用户库**：提供评论者昵称、头像等展示信息。

### 4.2 内部界面设计

#### 4.2.1 用户与权限管理模块

**调用关系：**

**数据接口：**

**数据接口：**

## 5 异常处理设计

### 5.1 出错信息管理

系统运行中可能出现的错误与异常包括：

1. 用户输入格式错误（空字段、密码过短、非法字符等）。  
2. 鉴权失败（Token 过期、未登录访问受保护接口）。  
3. 数据库连接失败或 SQL 执行异常。  
4. 媒体资源不存在、已下架或存储服务不可用。  
5. 上传文件超限、格式不支持或网络中断。  
6. 搜索无结果、评论过于频繁等业务逻辑异常。

**处理方法和策略：**

1. 前后端双重校验输入，返回统一错误码与友好中文提示，引导用户修正。  
2. 鉴权失败返回 401/403，前端跳转登录页，不暴露堆栈信息。  
3. 数据库操作使用 try-catch，记录错误日志，向用户展示"服务暂时不可用，请稍后重试"。  
4. 播放/拉流失败时提示"无法播放"并记录资源 ID，便于运维排查。  
5. 上传模块校验大小与 MIME，失败时保留已填元数据（若可行）并支持重新选择文件。  
6. 业务异常使用明确文案（如"该视频已下架""请先登录"），关键错误写入操作日志表或文件日志。

### 5.2 故障预防与补救

**可能导致系统故障的因素：**

1. 网络波动导致接口超时或视频卡顿。  
2. 数据库存储空间不足或连接池耗尽。  
3. 对象存储或流媒体节点异常。  
4. 代码缺陷导致未捕获异常。

**预防措施：**

1. 使用 Nginx 反向代理与健康检查；前端对超时请求重试（幂等读操作）。  
2. 定期备份 MySQL，监控磁盘与连接数；为常用查询字段建立索引。  
3. 大文件与点播/直播流分离部署，课程演示环境预留足够带宽与空间。  
4. 迭代开发与分模块测试，合并前进行集成测试。

**补救措施：**

1. 网络异常时提示用户检查网络并支持手动刷新。  
2. 数据库异常时切换只读提示或重启服务，从备份恢复（严重情况）。  
3. 存储不可用时降级为"暂不可播放/上传"，避免整站崩溃。  
4. 记录异常堆栈，修复后发布补丁并执行回归测试。

### 5.3 系统维护设计

**系统维护计划：**

1. 定期备份数据库与关键配置，清理临时上传碎片。  
2. 根据访问日志评估慢查询与热点接口，优化索引与缓存策略。  
3. 在课程验收前进行安全自查（弱口令、默认密钥、HTTPS 配置等）。

**问题处理策略：**

1. 用户或测试人员反馈问题后登记（问题描述、复现步骤、模块编号）。  
2. 按严重程度分级处理：阻塞性缺陷优先修复并再测试。  
3. 对影响演示的故障（无法登录、无法播放）启动紧急修复流程，并在文档中记录变更说明。

## 6 性能优化和安全设计

### 6.1 数据存储安全性考虑

- **数据加密**：用户密码采用 BCrypt 等单向哈希存储，不以明文保存。  
- **访问控制**：数据库账号按最小权限配置，应用层通过连接池访问，禁止公网直接暴露数据库端口。  
- **备份**：定期备份用户与业务数据，防止误删或损坏。

### 6.2 数据传输安全性考虑

- **加密传输**：生产或演示环境宜启用 HTTPS，防止 Token 与密码在传输中被窃听。  
- **完整性**：接口采用 JSON 等格式并校验 Content-Type；重要写操作可记录请求摘要便于审计。

### 6.3 数据访问安全性考虑

- **身份验证**：除注册、登录、公开列表等接口外，敏感操作需在请求头携带有效 JWT。  
- **权限控制**：发布、编辑、直播开播等接口校验角色（发布者/管理员）。  
- **审计日志**：记录登录失败、权限拒绝、上传失败等事件，便于发现异常访问。

### 6.4 性能优化考虑

- **数据库索引**：为 `users.username`、`videos.author_id`、`videos.status`、`comments.target_id`、`subscriptions.follower_id` 等高频查询字段建立索引。  
- **数据缓存**：对首页推荐列表、热门直播列表等只读数据可使用内存缓存（如 Redis，若实现）降低数据库压力。  
- **静态资源**：视频、封面等大文件通过 Nginx 或对象存储直出，减轻应用服务器带宽压力。  
- **分页与懒加载**：列表与搜索结果统一分页，评论与互动区按需加载，避免单次返回过大数据集。  
- **响应时间目标**：普通查询接口在课程环境下力争 200ms 内返回（与概要设计一致）。
